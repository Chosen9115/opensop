# OpenSOP 0.2 — Implementation Roadmap

> **Why v0.2 exists:** A round of dogfooding (the HermesOS mapping experiment) tried to express a real, running agentic system in OpenSOP 0.1. The 12 friction points it surfaced are codified in [`SPEC-v0.2.md`](../SPEC-v0.2.md). This roadmap is how we land them.

**Anchor goal:** *A `.sop.yaml` containing an `llm` step with `tools:`, `expected_output_schema:`, and `collection: true` outputs runs end-to-end against a real Anthropic Claude model, validates its output, retries on schema failure, and persists token cost.*

If we hit that, the rest of v0.2 is incremental.

---

## Phases

Each phase ships behind a flag (`OPENSOP_V02_<FEATURE>=1`) so 0.1 behavior remains the default until cut-over.

### Phase 1 — LLM-native execution `[anchor]` ✅ Shipped (2026-04-28)
Spec sections: §2.5, §2.6, §2.7

| Layer | Work | Owner |
|---|---|---|
| Models | New `Sop::LlmCall` (per-call audit row: step_id, model, prompt_hash, input_tokens, output_tokens, cost_cents, attempt, status) | `models` |
| Schema | Migration for `sop_llm_calls`; nullable `tools` column on `sop_steps` | `database` |
| Services | `Opensop::StepExecutors::Llm` — provider call, schema validation, retry-on-incomplete loop | `services` |
| Services | `Opensop::LlmProviders::Anthropic` (default) + base interface | `services` |
| Services | `Opensop::OutputSchemaValidator` — parses the mini-grammar, validates response | `services` |
| Services | `Opensop::ToolRegistry` — load from `opensop.config.yaml`, expose to providers | `services` |
| Services | `Opensop::DefinitionParser` — accept `opensop: "0.2"`, parse `llm` step, `collection:`, `item_schema:`, `tools:` | `services` |
| Services | `Opensop::InputResolver` — `[*]`, `[n]`, `.field` selectors on collection outputs | `services` |
| Tests | Llm executor + provider stub + schema validator + parser cases | `tests` |

**Definition of done:** `processes/v02-smoke-llm.sop.yaml` (a one-step llm process) runs via `POST /sop/v02-smoke-llm/start` with `ANTHROPIC_API_KEY` set; outputs validate; the LlmCall row records tokens and cost.

**Phase 1 follow-ups:**
- **alpha.5 (2026-04-28):** Shipped `validation:` field on `automated` steps (SPEC-v0.2.md §2.14). Opt-in `strict` mode presence-checks declared output names against the script's parsed stdout JSON, raising `StepFailure` on drift instead of silently emitting `null` and surfacing as a misleading "unresolved input reference" error downstream. Default remains `lenient` (current behavior). Surfaced by HermesOS dogfooding.

### Phase 2 — Control flow ✅ Shipped (2026-04-28)
Spec sections: §2.8 (`exit_when:`), §2.9 (`loop:`)

| Layer | Work | Owner |
|---|---|---|
| Schema | New `sop_step_iterations` table (parent_step_id, index, state, outputs, started/finished_at) | `database` |
| Models | `Sop::StepIteration`; loop-aware methods on `Sop::Step` | `models` |
| Services | `Opensop::StepExecutors::Loop` — for_each / repeat_until / while; aggregation | `services` |
| Services | Engine support for `exit_when:` + `exit_outputs:` in the advance loop | `services` |
| Services | Parser changes for `loop:` body, aggregation rules | `services` |
| Views | Loop iterations panel on instance detail (collapsed by default) | `views` |
| Tests | Loop variants + termination + aggregation; exit_when happy/sad paths | `tests` |

**Definition of done:** A loop process that runs an `llm` step once per item in a collection from a previous step, aggregates results with `concat`, and terminates correctly under all three loop variants. `exit_when:` short-circuits a process and writes literal exit_outputs.

### Phase 3 — Triggers & scheduling
Spec section: §2.10

| Layer | Work | Owner |
|---|---|---|
| DevOps | Adopt Solid Queue (Rails 8 default) for the scheduler backend | `devops` |
| Jobs | `Opensop::ScheduledTriggerJob` — fires per process per schedule | `jobs` |
| Services | `Opensop::Scheduler` — registers cron / interval / at: entries from loaded definitions | `services` |
| Services | Parser changes for `interval:`, `at:`, `timezone:` | `services` |
| Views | Triggers tab on process detail page | `views` |
| Tests | Schedule registration on registry reload; trigger fires once per window | `tests` |

**Definition of done:** A process with `trigger: { type: interval, interval: 30s }` starts a fresh instance every 30 seconds without API calls. Cron and multi-time `at:` work the same way.

### Phase 4 — Composition (fan-out)
Spec section: §2.11

| Layer | Work | Owner |
|---|---|---|
| Services | Extend `Opensop::StepExecutors::Subprocess` with `fan_out:` semantics | `services` |
| Services | `Opensop::ChildInstanceCoordinator` — launch N children, observe completion, aggregate | `services` |
| Services | `max_concurrency:` enforcement (semaphore via Solid Queue) | `services` |

| Views | Children tab on parent instance detail | `views` |
| Tests | Fan-out happy path + each `on_child_failure:` mode | `tests` |

**Definition of done:** A parent process that fans out 50 `enrich-lead` children with `max_concurrency: 5` aggregates their outputs into a single collection. Failure modes behave per spec.

### Phase 5 — State & observation
Spec sections: §2.12 (`post_review:`), §2.13 (shared state)

| Layer | Work | Owner |
|---|---|---|
| Schema | New `sop_shared_state` table (process_name, key, value JSONB, version, updated_at) | `database` |
| Models | `Sop::SharedStateEntry` with optimistic locking on `version` | `models` |
| Services | Resolver support for `instance.shared_state.<key>`; write-gate via `_shared_state.<key>` output prefix | `services` |
| Services | Engine: invoke `post_review:` step after terminal transitions; respect `failure_mode:` | `services` |
| Views | Shared State tab per process; Post-Review section on instance detail | `views` |
| Tests | Shared state read/write events; declared-only writes enforced; post_review modes | `tests` |

**Definition of done:** A process that reads `last_run_at` from shared state, skips work if recent, and writes back on completion. Post-review hook runs after every instance and surfaces flagged ones in the UI.

## Cross-cutting

| Concern | Notes |
|---|---|
| **Versioning** | `opensop: "0.1"` files use the 0.1 parser path; `opensop: "0.2"` files unlock new keywords. Mixing is allowed at the process level only. |
| **Backwards compat** | No removed keywords. No changed semantics on existing steps. New tables only — no destructive migrations. |
| **Feature flags** | `OPENSOP_V02_LLM_STEP`, `OPENSOP_V02_LOOPS`, etc. Flags removed when the feature is the default. |
| **CHANGELOG** | Each phase appends a `[Unreleased]` block. v0.2.0 is cut once Phases 1+2 land; 3/4/5 may ship as 0.2.x. |
| **Docs** | When a phase merges, fold its section from `SPEC-v0.2.md` into `SPEC.md` proper and update `docs/process-authoring.md`. |
| **Demo processes** | Each phase ships at least one `processes/v02-smoke-*.sop.yaml` exercising the new feature. |

## Out of scope for v0.2 (intentional)

| Item | Why not now |
|---|---|
| `async: true` steps | Engine is currently sequential. Concurrent step states + join semantics are large; let loops & fan-out reveal the shape first. Target v0.3. |
| Templates / `extends:` | Overlay/override semantics deserve a dedicated milestone. Target v0.3. |
| CAS shared state | Optimistic last-writer-wins is enough for v0.2. CAS in v0.3 if pain shows up. |
| LLM tool *enforcement* on `automated` steps | Declared and surfaced in UI (advisory). Real sandbox lands when it has a clear use case. |

## Phase 1 — kickoff order

These tasks have explicit dependencies; the parenthesized layer label maps to a specialist agent.

```
1. (database)  migration: sop_llm_calls + sop_steps.tools column
2. (models)    Sop::LlmCall + tools= accessor on Sop::Step
3. (services)  parse v0.2 keywords (llm step, tools:, collection:, item_schema:)
4. (services)  Opensop::OutputSchemaValidator
5. (services)  Opensop::LlmProviders::Anthropic (+ base)
6. (services)  Opensop::ToolRegistry
7. (services)  Opensop::StepExecutors::Llm — wires 3-6 into the executor
8. (services)  Resolver: collection selectors [*] [n] .field
9. (tests)     End-to-end: smoke process + recorded LlmCall row
```

Steps 4–6 are independent and can run in parallel once 1–3 land.
